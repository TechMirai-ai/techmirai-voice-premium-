## ⚠️ KNOWN ISSUE (OPEN, unresolved): web-call join fails from our `/vapi-test-call` page (2026-09-20)

**Status: OPEN AGAIN (step 14) — the "cause is the CSP" conclusion of steps 12–13 is WALKED BACK. On bare Express apps the CSP was implicated (CSP on failed, CSP off joined), but dropping the CSP from the real app did NOT make the main app join. So the CSP is at most part of the story; a further variable present in the real `app.ts`/process was never isolated (the owner's leading suspect: the Postgres pool). The standalone server (3001) remains the only confirmed-working page.** This replaces an earlier entry here that called it "intermittent Vapi/Daily-side flakiness, not our code". That conclusion is **withdrawn** — later evidence (below) shows success/failure correlates with *how the test page is served*, so our side is not ruled out.

**Symptom.** Starting a web call against the real `sakura-seikotsuin--ja` assistant (`5783f9a4-7051-4595-b391-997c080fc61b`) from `/vapi-test-call` fails client-side with `daily-error` → `{error:{type:"connection-error"}}` → `daily-call-join-error` (~6.7–7.1s) → `start-method-error`. Vapi records the call as `endedReason: call.in-progress.error-assistant-did-not-receive-customer-audio`, ~$0.0095 each (the browser never joined the Daily room). As of 2026-09-20: 45 call records, $0.5856 total across the whole investigation.

**Elimination sequence (in order):**
1. **CSP.** The route's helmet CSP blocked things in turn: widget icon (`img-src`), Vapi API + Daily transport (`connect-src`/`script-src`/`worker-src`), then Daily's Sentry beacon. All widened (commits `1abb1ea`, `0e69e35`, `238ed42`); a grep of the SDK's actual outbound origins was done rather than fixing one error at a time. Failure persisted.
2. **Opaque error.** The SDK threw a bare `Unhandled error. (undefined)`. Added a `vapi.on('error')` handler that logs the full object (`f49c37f`). This produced the `daily-error`/`connection-error` chain above.
3. **Network / browser / mic.** Same failure on two different real networks (owner's home + mobile) and in the dev sandbox; owner's mic/browser/network had already worked in the R7b call. Not a single network or machine.
4. **Assistant config.** A "stuck" assistant instance, `model.toolIds` at creation vs added later, and `maxDurationSeconds` unset (which flips Vapi's reported `latestVersion` v1→v2 but does not change join behavior) — each disproved. A byte-for-byte clone succeeded repeatedly; the exact assistant that had just succeeded 3× then failed on the next attempt with no changes.
5. **Served path.** Owner's key finding: **every success was served by a raw Python `http.server` sending no headers at all (R7b's probe pages); every failure was served by the real Express `/vapi-test-call` route** (helmet CSP and all), including a fresh clone of the assistant. → isolate Express.
6. **Plain `node:http` server on :3000 (no Express/helmet), same page, same real assistant.** **Succeeded 2/2** (owner-reported). So Express (or something Express adds) is implicated, not the page, the assistant, or port 3000.
7. **`curl -v` diff of the Express response vs the plain-Node response for the identical request.** Response **bodies were byte-identical**; headers were examined and **ruled out** as the cause (owner-reported).
8. **Exact `publicKey`/`assistantId` at `vapi.start()`.** Logged on a failing attempt: `publicKey` `6c0332a8-f3da-4dcc-8b6b-aef55d399b16` (Vapi's browser-safe public key), `assistantId` `5783f9a4-7051-4595-b391-997c080fc61b`; actual `start()` arguments `["5783f9a4-7051-4595-b391-997c080fc61b", null]`. Correct values, correct assistant. (A comparison against a *working* run's logged values is not recorded.) The logging stays in the bootstrap script.
9. **Express send path.** Swapped only `/vapi-test-call` to raw `res.end()` (no `res.send()`, no ETag; Node set `Content-Length`) — **still failed**, identically, in two independent environments: headless Playwright (7.1s) and the owner's real browser (`daily-call-join-error`, 6.7s). Reverted (`res.send()` restored). So neither the browser environment nor `res.send()` vs `res.end()` is the differentiator.

10. **`express.static()` (2026-09-20) — FAILED, same pattern.** Served the page as pre-generated static HTML+JS (`npm run vapi:test-page`, values baked in as literal text, no per-request logic) through `express.static()`, a different internal mechanism from `res.send()`/`res.end()` (file streaming, its own `ETag`/`Last-Modified`/`Cache-Control`). In the owner's real browser the **first attempt failed identically**: `daily-error` → `connection-error` → `daily-call-join-error`, ~6.6s. The planned 3-in-a-row run was stopped after that one failure. **Conclusion: `res.send()`, raw `res.end()` and `express.static()` all fail the same way, so the failure is not about how a response is built or sent** — it is something about our app process rather than how a response is built (step 11 then showed it is not Express itself either). Response-mechanism experiments stop here. The `express.static()` code was **kept** (it is simpler than the per-request route and made nothing worse); the standalone server below is the working path.

11. **Bare Express vs. standalone Node (2026-09-20) — both JOIN.** With the same generated page and assistant, in the owner's real browser: the standalone plain-`node:http` server (port 3001) **connected and played the greeting on the first try**, and a **bare Express app** (port 3002; just `express.static()` on the directory — no helmet, no `express.json()`, no CSP, no Postgres pool) **also connected and played the greeting on the first try**. **So Express itself is not the cause.** The only remaining difference between the failing app and a bare Express app is what `src/app.ts` adds: `helmet()` (including the widened test-call CSP), `express.json()`, the Postgres pool created in `server.ts`, or an interaction between them.

12. **helmet bisect (2026-09-20) — the CSP implicated (this reading was later walked back, see step 14).** Two bare Express apps (only `express.static()` on the generated directory; no `express.json()`, no Postgres pool), differing in a single thing, tested in the owner's real browser:
    - **Port 3003 — `helmet()` globally plus the widened test-call CSP on the mount, exactly as `app.ts` does: FAILED**, same `daily-error` → `connection-error` → `daily-call-join-error`.
    - **Port 3004 — `helmet({ contentSecurityPolicy: false })` (all of helmet's other headers, e.g. COOP/CORP/HSTS/Referrer-Policy, but no CSP): CONNECTED** and played the greeting.

    The only difference is the `Content-Security-Policy` header, so **that header — or how it is applied — is what breaks the join.** It is not helmet's other headers, `express.json()`, the Postgres pool, Express, or response mechanics (steps 9–11). Single attempt per server, so the small-sample caveat still applies, but it agrees with every earlier result (all failures went through a route with the CSP; all successes sent none).

    **Three more CSP variants, all FAILED** (same bare-Express + `helmet()` base as 3003, owner's real browser, 2026-09-20; earlier failing runs also logged **no** CSP "Refused to…" console errors, so the blocking effect is not a plain logged violation):
    - **Port 3005 — identical CSP with `upgrade-insecure-requests` removed** (set to `null`; helmet re-adds an omitted default directive otherwise): failed.
    - **Port 3006 — identical CSP plus `frame-src`/`child-src`/`media-src` (`'self'`, Daily origins, `blob:`, `data:`), `blob:` in `script-src`, and `blob:`/`data:` in `connect-src`:** failed.
    - **Port 3007 — identical CSP with `connect-src 'self' *`** (fully wildcarded, to rule out an unlisted STUN/TURN/dynamic host; `connect-src` does not govern WebRTC's own ICE traffic, so this only rules out unlisted fetch/WebSocket hosts): failed.

    So `upgrade-insecure-requests`, `connect-src` (even wildcarded) and the frame/media/blob widenings are each ruled out as *the* directive; which directive is responsible was not identified.

13. **Decision (2026-09-20, owner): drop the CSP from the `/vapi-test-call` route entirely.** The bisection was stopped deliberately at this point, not because it was solved. Reasoning:
    - It is an **internal QA-only page** — never customer-facing, never mounted in production, served by a localhost dev server, and it only serves static files we generate ourselves.
    - The CSP has **cost hours with no confirmed benefit** for this one route, and the only configurations known to join (3001–3004) send no CSP.
    - The blast radius is small and explicit: **every other route keeps helmet's full default CSP**, and the test-call route **keeps helmet's other headers** (COOP, CORP, `X-Content-Type-Options`, HSTS, …) — exactly the port-3004 configuration that joined.

    Implemented in `src/app.ts`: the test-call `express.static()` mount comes *before* the global `helmet()` and uses `helmet({ contentSecurityPolicy: false })`. Tests assert that the page and script send **no** CSP (so a future "add security headers back" change can't silently break calls), that helmet's other headers are still present, and that other routes — including a missing test-call file's 404 — keep the strict default CSP. The CSP origin lists and the Sentry-beacon audit that used to live in `testPage.ts` comments are kept below. **Superseded by step 14:** this change did not make the main app join, so it removed one suspect but is not the fix. It is kept in place (the route is an internal QA page and the tests document it), but the CSP is no longer believed to explain the failure of the full app. If a CSP is ever wanted back on this route, re-test with a real call.

14. **Main app STILL fails with the CSP dropped (2026-09-20, owner, real browser) — CSP walked back.** After step 13 (test-call route now sends helmet's other headers and no CSP, the same configuration as port 3004) the owner's run of the main app on port 3000 **still failed to join**. So "the CSP is the cause" is **withdrawn**: CSP on (3003) failed and CSP off (3004) joined on the bare app, but that was one attempt each, and removing the CSP did **not** fix the full app. The honest reading is that CSP is *implicated but not sufficient*, and **a real remaining variable in the full app was never isolated.**

## Decision for VP-2 (sync approach)
`VapiAI/gitops` is built around one static folder per Vapi org. We need one template → many clients. Default plan: our own small sync engine that renders `client.yaml` + shared templates into Vapi payloads and syncs them with `@vapi-ai/server-sdk`, copying the good ideas from `VapiAI/gitops` (name → UUID state file, dry-run, snapshot before push, no secrets in files). VP-2 must re-evaluate this in its PR before building.
