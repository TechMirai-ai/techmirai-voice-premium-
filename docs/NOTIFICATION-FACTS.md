# Notification facts (Telnyx SMS, LINE push, Vapi caller ID)

Facts the booking-notification code (VP-23, `src/notifications/`) relies on. Same rule as
`VAPI-FACTS.md`: verify against current docs before changing the code, and add what you verify
here with the source and date. **Status** says how each fact was checked — "live" means a real API
call, "docs" means read from the vendor's documentation only.

## Abuse guards (our own code, not provider facts)

Added after the VP-23 security review: the public `/talk` page lets anyone type a number, so a booking can text a stranger. All three guards live in `src/notifications/bookingNotifier.ts`; every limit is per client in `client.yaml`.

- **Destination allow-list** — `sms.allowedCountryCodes` (default `["+81"]`, Japan only). A number outside it is logged `skipped` / `country_not_allowed` and nothing is sent. `defaultCountryCode` must be one of them. A code is matched as a prefix and must be 2–3 digits, except `+1` and `+7` (the only one-digit calling codes) — so a stray `"+8"` is rejected at config load instead of admitting China, Korea and Vietnam. Note `"+1"` admits every North American Numbering Plan country, including the Caribbean and premium-rate ranges.
- **Daily caps** — `sms.maxPerDay` (100), `sms.maxPerRecipientPerDay` (3) and `line.maxPerDay` (50), counted over a rolling 24 hours. Over a cap → `skipped` / `daily_limit` (whole client) or `rate_limited` (one number).
- **One SMS and one LINE alert per call** — a Vapi call (`call_id`, joined through `appointments`) may produce at most one of each; a second booking in the same call is logged `skipped` / `call_limit`. This is a fixed rule, not a setting. It is what stops one public call from burning the whole daily budget and silencing real patients and staff; a caller who genuinely books twice in one call gets one confirmation (both bookings are still saved and visible to staff).
- **LINE is capped per booking, not per recipient** — one `pending` row is reserved per booking and then fanned out to every recipient whose variable is set (`recipient_ref` lists their env-var names, comma-separated). `line.maxPerDay` therefore counts alerts, never individual pushes, so adding a recipient does not shrink it and a cap hit can never tell some staff and not others. The row ends `sent` if at least one recipient was reached (`detail` = `partial_failure` when some were not) and `failed` only if none were. A recipient with no variable set is logged `skipped` / `missing_credentials` on its own row and does not count.
- **Race-safe by reservation** — each send first inserts a `pending` `notification_log` row, then counts live rows, then sends and settles the row (`sent` / `failed`). The request that counts last sees every other request's reservation, so simultaneous bookings cannot exceed a cap; two at once may both be refused, which is the safe direction. A `pending` row older than 5 minutes (a crashed or timed-out request; a live send takes seconds) stops counting, so it cannot hold a slot for a day — the rare crash-after-send case can therefore allow one extra message, which is accepted. If the log database is unreachable the caps cannot be checked, so the send is skipped (fails closed) and the error is logged.
- **Visibility** — hitting the whole-client daily cap logs a `warn` (`notification daily cap reached`, with `clientId`, `channel`, `maxPerDay`, no personal data), because from then on real patients and staff go without that channel until the 24 h window rolls. `call_limit` and the per-number `rate_limited` do not warn.
- **Staff alert text** — caller-supplied text (`[[patientName]]`, `[[serviceName]]`) is put on one line: invisible Unicode format characters (bidi overrides, zero-width characters, soft hyphen) are dropped, control characters and line breaks become a space, whitespace collapses, 100-character cap, and a value that ends up empty shows `-` (`sanitizeInline` in `src/notifications/template.ts`).

**Deploy order:** run `npm run db:migrate` on the production database (applies `0014_notification_log_pending.sql`) BEFORE or together with deploying this code. New code on a database without 0014 fails every reservation insert, and because the guards fail closed, ALL SMS and LINE sends silently stop (an error is logged; bookings are unaffected). Old code on the new schema keeps working. There is no down migration.

**Manual step (not code):** set a **spend limit / auto-recharge ceiling on the Telnyx account** in the Telnyx portal. The caps above bound how many messages the app will send, but only a provider-side limit bounds the money if the app is bypassed (for example someone calling Vapi directly with the public assistant id). Not verified here and not settable by this repo.

Not covered yet (follow-up): a typed `/talk` number is still untrusted, so a direct Vapi call can still make the clinic text a Japanese stranger, up to the caps; sending only to a carrier-verified caller ID would close that.

- V1–V2: `callerPhoneFromCall` in `src/vapi/callVariables.ts`.
